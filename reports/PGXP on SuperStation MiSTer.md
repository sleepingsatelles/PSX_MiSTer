**PGXP feasibility on the Retro Remake SuperStation**

**The idea has been discussed, but this investigation found no public, installable PGXP implementation for the MiSTer PlayStation core.** Assuming your console is the **SuperStation One**, its MiSTer compatibility makes it a plausible target for a future compatible build. An optional enhancement with unchanged game performance is a reasonable engineering goal, but there is no measured implementation here that establishes it. Full PGXP would require substantial changes inside the core, and “no impact in any other way” is a stronger requirement than maintaining frame rate. Research checked public projects and documentation on October 3, 2026; private or unindexed experiments remain unknown. ([Official PSX features](https://github.com/MiSTer-devel/PSX_MiSTer/blob/main/README.md), [SuperStation One](https://retroremake.co/pages/superstation%E1%B5%92%E2%81%BF%E1%B5%89))

There is historical evidence that the developer considered part of this problem. A **May 2, 2022 RetroRGB report** attributed the absence of perspective correction to the developer judging its cost too high for MiSTer. The original linked discussion could not be retrieved, so this is contemporary secondary reporting, not a verified current developer statement or a quantified feasibility study. It addresses perspective correction specifically; it does not prove every narrower geometry-stabilization approach is impossible. The reviewed official feature list, top-level source, release listing, and Retro-Remake fork did not reveal a PGXP option or build. Existing texture filtering, widescreen, and 24-bit rendering are different enhancements. ([RetroRGB report](https://retrorgb.com/mister-fpga-news-updates-new-public-jotego-cores-psx-filtering-32x-sound-fix-more.html), [Official core options](https://github.com/MiSTer-devel/PSX_MiSTer/blob/main/PSX.sv), [Releases](https://github.com/MiSTer-devel/PSX_MiSTer/tree/main/releases), [Retro-Remake fork](https://github.com/Retro-Remake/PSX_MiSTer))

PGXP comprises several corrections. Retaining subpixel vertex positions can reduce polygon wobble; perspective-correct textures additionally need depth information to address texture warping. The inspected core discards fractional screen-coordinate bits at the GTE output, while its polygon renderer receives integer positions without a depth field. Keeping those fractions is a starting point, but the difficult part is following each vertex through CPU operations, memory, and DMA until the GPU receives it. DuckStation's actual PGXP implementation illustrates this: it maintains extra precision metadata, validates recovered vertices, and falls back to original coordinates when needed. This is work inside the geometry and rendering pipeline; a final-image filter cannot exactly reconstruct the missing coordinates and depth. ([Local GTE source](/Users/cwagner/Documents/projects/PSX_MiSTer/rtl/gte.vhd:1311), [Local vertex format](/Users/cwagner/Documents/projects/PSX_MiSTer/rtl/gpu_poly.vhd:131), [DuckStation PGXP implementation](https://github.com/stenzek/duckstation/blob/master/src/core/cpu_pgxp.cpp))

**FPGA parallelism makes unchanged game timing conceivable, but does not establish free capacity.** This is an engineering inference: extra logic could run alongside the original path if it fits and meets every deadline. It still consumes logic, memory, routing, and potentially bandwidth. In this core, rendering completion and GPU readiness interact with DMA, so extra rendering work can affect guest execution. Corrected pixels can also affect games that read VRAM or reuse rendered imagery as textures. Strictly identical game-visible behavior might require preserving canonical rendering separately from enhanced presentation, increasing cost further. No synthesis utilization report, timing analysis, benchmark, or tested prototype was produced, so neither “the FPGA is full” nor “it has sufficient spare resources” is justified. ([Local GPU readiness logic](/Users/cwagner/Documents/projects/PSX_MiSTer/rtl/gpu.vhd:978), [DMA request handling](/Users/cwagner/Documents/projects/PSX_MiSTer/rtl/dma.vhd:216), [VRAM operations](/Users/cwagner/Documents/projects/PSX_MiSTer/rtl/gpu.vhd:988))

A credible development experiment would begin with **geometry stabilization only**, retain original GTE registers and flags, track precise vertices alongside memory operations, and fall back to native geometry whenever tracking fails. Perspective texture correction would follow only after that smaller design fits and works. An Off setting should restore baseline behavior, but even disabled added circuitry can affect FPGA timing closure; retaining the stock bitstream remains the clearest fallback. Validation needs synthesis and actual hardware tests plus comparisons of GPU status, DMA and interrupt timing, audio, and game compatibility—not FPS alone. This is a proposed research path, not an available feature. DuckStation's separate PGXP controls and game-specific fallback behavior reinforce the need for compatibility testing. ([DuckStation graphics settings](https://github.com/stenzek/duckstation/blob/master/src/duckstation-qt/graphicssettingswidget.cpp))

For installation, Retro Remake confirms a Cyclone V FPGA, 128 MB SDRAM, and full MiSTer support for SuperStation One. That establishes platform compatibility, not extra headroom for PGXP. **There is currently no verified PGXP RBF from this investigation to install.** A future validated build should first be tested from a spare SD card or separate MiSTer menu entry, preserving the working setup. It would also need checks for your native controllers, memory cards, video output, and any Console Mode or dock integration. Separate filenames alone do not necessarily isolate configuration and saves. No core, firmware, or console files were changed during this research.
